# Runbooks

How to write a runbook, upload it, and read what the core says about it. This is the author's guide for alpha.17: the file format, the two switches, and how validation reads. **There is no runner yet in this alpha** — see [What is not built yet](#what-is-not-built-yet) before you go looking for one.

Source: `src/personacore/web/screens/runbooks.py` (the admin screen), `src/personacore/web/screens/core.py` (the core switch), `src/personacore/web/screens/plugin_detail.py` (the per-plugin switch). The file format and the validator are their own package, `src/personacore/runbooks/`.

## What a runbook is

A runbook is a YAML file: a self-describing, ordered list of steps the core runs inside one conversation, reporting progress in the chat as it goes and stopping wherever a step asks the person a question. Think "Ansible for the assistant" — the core provides one generic ability, *run a runbook*; a plugin provides the tools a runbook calls; the runbook itself may be written by hand, generated by a persona, or bundled with the plugin it drives.

A runbook says what it needs — which plugin, at what minimum version, which tools — so the only thing left to go wrong once it is uploaded is the author's own mistake, and the validator tells you which line that is.

## The file, field by field

A complete, working example — a fictional runbook for a fictional `storybook` plugin, using every field this format defines, with a human gate and an automatic one:

```yaml
runbook: daily-summary          # identifier: [a-z0-9-]{1,40}; also the file name (daily-summary.yaml)
version: 1.0.0                  # the runbook's own semver, shown in the picker; a second upload of the
                                 # same id keeps whichever is newer
format: 1                       # the runbook FORMAT this file is written against — the core refuses a
                                 # file declaring a format newer than it understands
title: Daily summary
description: >
  Fetches today's pages, drafts a one-paragraph summary, and stops once for a
  human check before saving it.

requires:
  plugins:                      # plugin name -> minimum version, as a PEP 440 / semver specifier.
    storybook: ">=2.1.0"        # Every plugin named here must be installed, switched on (both the core
                                 # switch and that plugin's own runbooks switch — see below), and at
                                 # least this version, or the picker greys the runbook out with the reason.
  tools: [storybook.fetch_today, storybook.save_summary]   # each must be a tool storybook declares
persona: editor-in-chief        # optional default persona; the picker lets the person change it

inputs:                         # asked as a small form before the run starts
  - name: audience
    type: string
    default: household
    prompt: Who is this summary for?

steps:
  # kind: tool — calls a plugin tool with fixed arguments. Confirm-risk tools
  # are refused here exactly as they would be refused in chat.
  - id: fetch
    kind: tool
    tool: storybook.fetch_today
    args: { audience: "{{ audience }}" }
    files:                      # names the file(s) this step is expected to leave, BY ROLE — never a
                                 # literal filename a later step has to know
      pages: "today.md"
    pin: [pages]                 # these roles carry forward automatically to every later step,
                                 # without each one having to repeat them in its own `pins:`

  # kind: model — one scripted turn against a prompt file (or `prompt_text:` inline).
  - id: draft
    kind: model
    prompt: prompts/draft.md    # relative to the runbook file itself
    thinking: off
    temperature: 0.4
    pins: [pages]                # the "pages" role from the fetch step, pinned into this turn
    output: "summary-draft.md"   # the reply is written here; its own role is the step id ("draft")
    watchdog: { max_output_tokens: 800, max_seconds: 120 }   # trip on whichever limit is hit
                                 # first; `max_output_ratio` (of the input size) may stand in for
                                 # `max_output_tokens` — see "Watchdog, endpoint, apply and then" below

  # `endpoint:` sends this turn to a named LLM role from core.toml instead of
  # the conversation's own model — falls back to `interactive` when absent.
  - id: review
    kind: model
    prompt: prompts/review.md
    thinking: on
    endpoint: audit
    pins: [draft, pages]
    output: "review-notes.md"

  # kind: gate — stops and asks, or checks an automatic condition. This one asks.
  - id: check
    kind: gate
    from: review                  # the file the questions are drawn from
    questions: model               # "model": the persona turns the notes into a question; "file":
                                    # the step's own file is already the question JSON (see below)
    answer: "checked.md"           # role: "checked"

  # `apply:` turns the reply into an edit onto an earlier step's own file instead of a
  # fresh draft; `then:` loops the run back to that earlier step's id afterwards.
  - id: revise
    kind: model
    prompt: prompts/revise.md
    thinking: off
    pins: [draft, checked]
    output: "summary-revised.md"
    apply: { anchors: "¶", onto: draft }   # the reply is `¶N → replacement` lines; the runner
                                            # applies them by key onto the "draft" role's file
    then: draft                            # after applying, the run treats "draft" as current again

  # kind: gate, the `auto:` form — no person is asked; the run passes or loops on a
  # parsed condition over the named file.
  - id: polish-gate
    kind: gate
    from: revise
    auto:
      pass_when: "no line contains 'TODO'"
      else: { goto: revise, max_loops: 2 }     # otherwise loop back, at most twice

  - id: save
    kind: tool
    tool: storybook.save_summary
    args: { file: "{{ files.draft }}" }
```

### Rules that hold for every runbook

- **Roles, not filenames.** Every file a step produces is named once, by role, in that step's `files:` or `output:`. Every later step says `pins: [role, …]` to receive it — never a literal path. The runner labels each pinned block `pinned as [role] (filename)` so the model always knows what it is looking at. A prompt that has to be hand-edited per run because it names a file is a defect in the runbook, not a limitation of the runner.
- **Templates are `{{ input_name }}` and `{{ files.role }}` only.** No expressions, no arithmetic, no filters.
- **Three step kinds and only three:** `tool` (calls a plugin tool with fixed args), `model` (one scripted model turn), `gate` (asks a question, or checks an automatic condition — see below).
- **A step writes exactly one new file** (or the files a `tool` step's own contract says it hands back). Nothing is ever overwritten.
- **`thinking:` is `on` or `off`**, sent per request for a `model` step. There is no numeric budget — that is the model server's own concern.

### Gates

A `gate` step either asks a person, or checks a condition automatically:

```yaml
- id: check
  kind: gate
  from: review             # the file the flags/questions are drawn from
  questions: model         # or "file" — the step's own file is already question JSON
  answer: "checked.md"     # role: checked
```

```yaml
- id: polish-gate
  kind: gate
  from: revise
  auto:                                          # no person asked at all
    pass_when: "no line contains 'TODO'"          # a parsed condition over the named file
    else: { goto: revise, max_loops: 2 }          # otherwise loop back, at most twice
```

A `questions: model` gate runs one extra, silent model turn (thinking off) that turns the named file into a small set of questions, each with two to four click options and an **Other** box for typing — the person's picks and typed answers become the step's own answer file, and the next step can pin it like any other role. Nothing reads a typed **Other** answer as an instruction; it is data, the same as every other file a step produces. A `questions: file` gate skips that extra turn: the named step's own file is already the question JSON.

### Watchdog, endpoint, apply and then

Four more fields, all on `model` steps (the `draft`, `review` and `revise` steps above use one each):

- **`watchdog:`** trips a `model` step that runs away — one length limit and a time limit, together: either `max_output_tokens` (an absolute count) or `max_output_ratio` (a multiple of the input size), **plus** `max_seconds`. Whichever limit is hit first stops the turn; the partial reply is kept as `<output>.partial` and the run parks with the reason. There is no default — a step with no `watchdog:` runs unwatched.
- **`endpoint:`** names an LLM role from `core.toml` (`interactive`, `triage`, or a custom role such as `audit`) to run this one turn against, instead of the conversation's own model. Omit it and the step uses `interactive`.
- **`apply:`** turns the reply into an edit rather than a new file: `{ anchors: "¶", onto: <role> }` means the reply is a list of `¶N → replacement` lines, and the runner applies them by key onto the named role's own file instead of writing `output:` as a fresh one.
- **`then:`** jumps the run back to an earlier step's id once this step (and its `apply:`, if any) is done — the same kind of jump a gate's `auto: { else: { goto: … } }` makes, just declared on a `model` step instead of at a gate. Combined with `apply:`, this is how a runbook loops a revision pass over one file without a gate in between.

### Versions and `requires`

- `version` is the runbook's own semver. Uploading a new copy of an `id` already on this plugin keeps whichever version is newer; it does not create a second file.
- `requires.plugins` is a plugin name mapped to a minimum-version specifier (`">=2.1.0"`, PEP 440 / semver). Every plugin named must be **installed**, **switched on**, have **its own runbooks switch on** (see below), and be **at least this version** — all four, or the runbook is greyed out with the specific reason, on both the picker (once one exists) and this screen.
- `requires.tools` lists the exact tool names the runbook calls. Each must be declared by one of the plugins in `requires.plugins`.
- `format` is the runbook file format itself, not the runbook's own version. A file declaring a `format` newer than this core understands is refused outright — that is a core upgrade, not an authoring mistake.
- `persona` (top-level, optional) is the default persona the picker pre-selects for this runbook; the person running it can still change it before starting.

## The two switches

Running a runbook (once a runner exists — see below) needs **both** of these on. Both default off, and neither can be turned on by a plugin's own manifest, a bundled file, or an upload — only a person, from these two screens:

1. **The core switch — Core settings → Runbooks → "Runbook runs".** Off by default. While it is off: uploading, listing, validating and deleting all still work; only running is gated (and there is no runner at all yet in this alpha, so this makes no practical difference today). The Runbooks screen shows *"Runbook runs are off. Turn them on in Core settings."* while it is off.
2. **The per-plugin switch — on that plugin's own settings page, "Runbooks enabled".** Shown only for a plugin whose manifest declares `[runbooks] supported = true`. Off by default, and greyed with *"runs are off in Core settings"* while the switch above is off. A runbook belonging to a plugin whose own switch is off is listed but greyed, with *"runbooks are off for this plugin"* beside it.

The core switch overrides everything below it: turning the per-plugin switch on means nothing while the core switch is off.

## Uploading

On the **Runbooks** screen (under **Plugins** in the sidebar): pick a plugin from the selector — it only offers plugins that declare `[runbooks] supported = true` — then choose a file and upload it.

- **A single file** is a plain `.yaml`.
- **A runbook with its own prompt files** (any `model` step using `prompt: prompts/…`) uploads as a `.zip` containing the runbook's `<id>.yaml` at the top and a `prompts/` folder beside it holding the referenced `.md` files. Nothing outside those two shapes is accepted — no absolute paths, no `..`, nothing that would land outside the plugin's own runbooks folder.
- **Only `.yaml`, `.yml` or `.zip`** (checked on the filename, case-insensitively) is accepted at all — anything else is refused before it is even read, with *"A runbook is a .yaml file or a .zip holding one."*
- **2 MB is the limit**, per file. A larger upload is refused before the store ever sees it, with *"That file is larger than 2 MB, which is the limit for a runbook."*

Both refusals land back on this same page — nothing is stored, and neither is ever a server error.

Validation runs the moment the file lands, before it is ever listed as valid:

- The YAML parses and matches the schema above.
- Every step id is unique.
- Every `pins:` role was produced by an earlier step — "step p2 pins role `lint`, but no step produces it" is exactly the kind of sentence you get back, naming the step and the role.
- Every `goto` and `from` target names a real step.
- Every prompt file a `model` step names is actually present (in the `.zip`, or already on disk for a bundled reinstall).
- `format` is one this core understands.

**A refusal never destroys anything already there**, and it is always plain English — the sentences above, verbatim, on the page. Nothing about an invalid upload ever produces a server error; it produces a list of problems.

A bundled runbook — one that came in with the plugin's own package rather than an upload — is validated the same way, but a bad one is a **warning, not a refusal**: it is copied in and listed with its problems, and the plugin itself installs and runs exactly as if the runbook were not there at all.

## Reading the Runbooks screen

Each row is one runbook, on one plugin: its title and id, its own version, a **Requires** column listing each plugin it needs and the version specifier (`storybook >=2.1.0`, one line per plugin), an **Installed** column with what is actually on this core (`storybook 2.0.4`, or `storybook not installed`), whether it came bundled with the plugin or was uploaded separately, and a **Verdict** — either **Compatible** or the specific reason it is not (*"storybook 2.0.4 installed, runbook needs >=2.1.0"*, say). An invalid file shows its problems in place of a verdict; a row whose plugin has its own runbooks switch off is greyed with that reason.

Delete asks first, on a page of its own — naming the runbook and what is being removed — and works with scripting off. Deleting an uploaded runbook removes it for good; deleting a bundled one removes it until the plugin is reinstalled, which restores it from the package again.

## What is not built yet

This alpha (alpha.17) is upload, list, validate, delete, and the two switches above — nothing more. Explicitly **not** part of it, and not reachable from anywhere in the admin UI yet:

- **There is no runner.** Nothing executes a step. Turning both switches on changes nothing observable beyond what this screen and the per-plugin page show.
- **No picker.** The **+** control in the chat window that will one day list runbooks by plugin and start one does not exist yet.
- **No gates actually running**, no resume after a restart, no watchdog, and no progress lines in chat — all of §3–§5 of the design contract are future alphas.
- **No plugin-specific tools or bundled runbooks beyond the reference ones.** A plugin that adds its own tools, its own bundled runbooks, or its own persistent-memory integration to work with them is that plugin's own work, delivered as a package — not the core's.
