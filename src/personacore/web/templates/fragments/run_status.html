{# fragments/run_status.html — a runbook run's own live status line in the chat window (contract runbook.md §3 "Progress in the chat"; PLAN.md web row, alpha.19). The transcript's own `system`-role notice lines (chat_thread._notice_entry, drawn by fragments/chat_exchange_body.html) are the run's *history* — one line per step, written once and never redrawn. This is its *now*: what `chat_run.runbook_run_view` last found when this was rendered, with the one control (Stop while running, Resume while interrupted or parked on a failure) that line owns. Never works anything out for itself — every field comes off that one dict, so the full page, the poll and a Stop/Resume's own response can never disagree about what a run is doing. POLLS ITSELF ONLY WHILE THERE IS SOMETHING LEFT TO SAY: `hx-get`/ `hx-trigger` are on this element only when `run.poll` is true, and an `outerHTML` swap replaces the whole element — attributes included. A run that has nothing left to report (no run at all, parked, stopped, done or failed) renders without them, which is what stops the polling; nothing else has to notice that a second time. Context: run {visible, poll, cid, message, show_stop, show_resume, stop_url, resume_url, gate: {question_id, text, options: [str], other (bool), index, total, context: [{ref, quote}], flag_line (str|None), source_file (str|None), source_url (str|None)}|None, items: [{value, status, reason, link}], turn_running (bool)}, oob (bool — true when this is an out-of-band replacement, chat_messages.html switching threads) — see chat_run.runbook_run_view. `turn_running` (chat_run._fragment's own addition, not `runbook_run_view`'s) says a chat turn is registered and running in this conversation *right now* — `chat_turns.running_turn`, not this run's own `status`. The two differ exactly when they matter most: a run moving from one model step to the next ends one turn and starts a fresh one (`chat_turns.begin_turn`) while `status` reads `running` throughout, and a page that attached to the first turn has nothing pointing it at the second — its own `data-turn-running` was consumed once, at page load. This fragment is what is left polling (`run.poll` below) for as long as the run is running, so its own swap is chat.js's one remaining chance to notice and reattach (`attachIfMarked`). `gate` and `items` are WAVE2.md's own additions — "Gate questions in the chat" and a parent run's own progress lines — and each pre-empts the plain message/Stop/Resume line below; `runbook_run_view` never sets more than one of the three on a single view, so this template does not have to reconcile them. `gate.context`/`flag_line`/`source_file`/`source_url` are contract runbook.md §4's own addition, added 2026-09-05: a question without its evidence could not be answered ("is the timeline consistent between ¶24 and ¶36?" with neither paragraph in sight), so every passage the question is about is quoted under it, the flag line it came from is shown under the options, and a link opens the file itself. Every string here is untrusted model or workspace output — no `|safe` anywhere in this block, Jinja's own autoescaping is what makes that safe to print. #}
